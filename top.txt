1. Est-ce un problème pour l'App Store / Play Store ? → NON
C'est un pattern ultra-courant et explicitement autorisé sur les deux stores. La règle clé :

Règle	Statut
Apple 2.5.2 "pas de code exécutable téléchargé"	✅ Un fichier SQLite, c'est de la donnée, pas du code. Aucun souci.
Apple 2.1 "l'app doit être fonctionnelle au lancement"	✅ Ton app marche sans la base (recherche en ligne en fallback). La base locale est un bonus, pas le cœur. C'est la condition à ne PAS violer.
Apple — téléchargement cellulaire	⚠️ 12-18 MB c'est petit, mais bonne pratique : proposer WiFi ou demander. Pas un blocage.
Google Play	✅ Aucune restriction. Google ENCOURAGE même de sortir les gros assets de l'APK.
Sécurité (donnée extractible)	✅ Tu ne stockes QUE du public (noms/marques/scores). Zéro secret, zéro donnée user. Conforme à ce que tu disais.
Verdict : zéro risque de rejet, tant que (a) c'est de la donnée SQLite, (b) l'app reste utilisable sans, (c) tu respectes le cellulaire.

2. Comment le faire simplement (tout gratuit)

Génération (toi, 1 fois + cron mensuel)
  Postgres → dump des 6 colonnes légères → fichier .db SQLite + index FTS5 → gzip
       ↓
Hébergement : Supabase Storage (bucket public "catalog-db")  ← gratuit (1 GB inclus)
       ↓
App : expo-file-system télécharge le .gz → décompresse → expo-sqlite l'ouvre
       ↓
Recherche locale instantanée (0 ms, 0 requête serveur, marche hors-ligne)
3 briques, toutes gratuites :

expo-sqlite : lecture locale + FTS5.
expo-file-system : download + décompression.
Supabase Storage (bucket public) : héberge le .db.gz. Inclus dans ton plan.
Sync future = re-générer le .db 1×/mois et bumper un numéro de version ; l'app re-télécharge si version locale < version serveur. (Le delta updated_at ligne-par-ligne est plus complexe — je le déconseille au début, un remplacement complet mensuel de 15 MB est plus simple et suffisant.)

4. Comment tenir les 60-80 MB
C'est déjà calé par construction : on exclut les 2 colonnes lourdes (ingredients_text, image_url). Les ingrédients/image se chargent du serveur au tap sur un produit (1 requête, pas 400k). Résultat : 49 MB données + ~25 MB index FTS = ~75 MB disque, ~15 MB téléchargé.

⚖️ Mon avis honnête sur le séquençage
Après la Phase 1 (index réparé), la recherche serveur passe à ~15 ms. Donc la base locale n'apporte plus de la vitesse (le serveur est déjà rapide) — elle apporte le hors-ligne + zéro charge serveur. Pour "10 000 users simultanés", la Phase 1 + le cache KV (Phase 4) suffisent déjà largement.

La base locale devient alors un vrai plus produit (instantané + offline + serveur déchargé à ~0), mais c'est la brique la plus lourde en dev/maintenance. Donc :
